2 · Connect ≠ authenticate ≠ commit — the three-rung ladder

The tension you identified (login vs wallet binding both "sign a message", but the statement differs) resolves cleanly into three rungs, each with its own UX surface and its own cost to the user:

1 · Connect welcome card

WalletConnect pairing only. Zero signatures, zero obligation. Purely convenience: your accounts are ready in every game; later feeds auto-add (ENTRY-AUTOADD1). Spoofable and that's fine — it gates nothing.

2 · Authenticate generic modal

One signature: "I confirm that I control account X." No expiry/scope/publish options — retention is Katomia's call (30 days), because this is our bookkeeping need, not a user commitment. Offered contextually (post-feedback today), never demanded at the door.

3 · Raise commitment existing

The full binding: intent-key authorisation, expiry, scope, publish. Discovered via the carrot — you want reputation on your orders and access to members-only markets, so you find it in the profile. Unchanged.

Decision recorded: no signing at the door. The door invites connection; authentication is a bolt-on that appears where it earns its click (feedback attribution first). Do not collapse rungs 2 and 3 — the wire format is shared (same kpay.authChallenge envelope, same /authenticate store), but the user-facing statements stay distinct.

The retro-attribution trick (worth an FAQ entry when testers ask): feedback is already signed by the browser's intent key at send time. Authenticating afterwards binds that key to an account — so earlier feedback becomes attributable retroactively. That's why "send first, offer authentication after" costs nothing in integrity.

3 · The levers — site access as configuration ENTRY-GATING1

Nothing is gated today, deliberately. But the model to build when a lever is first pulled is agreed:

// site-config.json — sketch only, NOT implemented
"access": {
  "groups":  { "admin": "backend:katomiaAccountGroups", "testers": "..." },
  "routes": {
    "/":         { "require": "open" },          // open | connected | authenticated
    "/welcome":  { "require": "open" },          //   | group:<name> | tokens:<spec>
    "/create":   { "require": "authenticated" }, // example tightening
    "/board/*":  { "require": "open" }           // game links ALWAYS work (principle)
  },
  "redirect": "/welcome"   // where a refused route sends you (the sign-up funnel)
}
  • Purpose is demand throttling, not security — positive friction that routes hot demand through a sign-up/questionnaire/token-purchase funnel with customer-research value. Say this internally; externally it's just "member access".
  • Global position across ALL connected accounts (plural, always an array) decides page access — never a single account. In-game rules may differ; that's joinRule's domain and stays separate.
  • Token-held gating (tokens:<spec>) slots in as just another requirement type — this is where the research doc's findings (how Kabila & co. specify token gates) inform the spec shape.
  • Shipped groundwork it composes with: the backend already resolves commitments → accounts → groups for gated markets (GAME-JOINRULE1); page-level gating reuses the same identity plumbing, so the modal + bindings shipped today are the prerequisite layer.

4 · Feedback: trust tiers, Freddie, and the isolation question

You asked for advice on Freddie-with-branches vs a separate agent for tester feedback. Recommendation:

Recommended: one pipeline, separate prompts/workers per trust tier, isolation by tier

TierWhoProcessorEnvironment
staff/adminadmin group (exists)Freddie as-ison-estate (status quo; isolating even this is cheap defence-in-depth later)
testerstesters group — authenticated + curated (XProof/Twitter-assisted vetting)separate worker + its own prompt, shared plumbing/inbox formatring-fenced (container or small separate castle) — ENTRY-FREDISOLATE1
customersanyone authenticatedsame worker shape, stricter prompt (aggregate/digest only)strictly isolated, one-way queue out
anonymousno live commitmentcounted in aggregate metrics only; no LLM free-text processingn/a

Why not branches inside Freddie: the trust boundary is exactly a prompt-injection boundary, and a branch in one prompt is the weakest possible wall — one jailbreak in tester text reaches admin-grade tooling. The existing feedbackTriage.js already draws the hard line at the admin group ("only ever sees pre-authenticated admin input"), so the architecture already agrees: keep that property by giving each tier its own worker with its own (least-privilege) capabilities, not one worker with a switch. Vet-harder vs harden-systems: do both asymmetrically — vetting keeps the tester tier small and survivable early, isolation is what scales to customers, and it's the same container either way.

  • Shipped hook: unauthenticated feedback now triggers the authenticate offer (screenshot above) — the copy leads with the benefit ("counts toward your account and groups"), not the security rationale, exactly as you framed it.
  • "Publish my feedback" checkbox (not built): keep the plain wording — it's a question about sharing, orthogonal to AI processing. Default unchecked; unpublished feedback still counts in aggregate metrics. Possible carrot: published feedback earns more points. decide at feedback-v2
