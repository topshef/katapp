Decisions (user, 2026-08-17) — this doc's open questions are answered; sections below are kept for the record but superseded where they conflict:
  • Not a literal body. The analogy doesn't map cleanly — the visual is a building (facade at the top, Hedera foundation at the bottom) or simply "a diagram". First cut now live on results.html, driven by data/modules.json.
  • Grouping = tags, not nesting. A suite carries a modules array; one module = unit-scoped, several = end-to-end, drawn as a riser/pipe across the layers it touches. Registry: data/modules.json; suite tags in data/tests.json.
  • z = timestamp, always. Not commit-granular: every run sits at its real time; staggered sequential runs read as a staircase when rotated. Commits (and other non-test events: crons, restarts) layer onto the same timeline as events, so "commit → boom boom boom tests" is visible structurally — a run needs no assigned commit, though the run row keeps a trigger (commit / cron / manual) that links to the thing itself.
  • Environment is a run attribute, not a page. Each environment's QA folder stays self-scoped and self-aware (pages now show their hostname); a separate, generic tool — possibly its own repo — ingests the JSON from several environments and renders the 3D/WebGL (and Quest/WebXR) views. The repo owns its shape and tests; visualization is external.
  • Assertion-level cells: keep the data granular, decide at render time (cluster → expand on approach, like the task cluster graph / a flower reading sad from a distance).
  • Sequencing: list + grid first, reviewed and confirmed, before any further view. The 3D volume is parked until the data model has settled.

The original idea (2026-08-16): stop reading QA as a spreadsheet and start reading it as a body. Modules are limbs and organs; each organ is a small heat map whose cells are individual test instances; the whole figure is the health of the application at a glance. History is the same figure repeated backwards through time — first as a filmstrip, ultimately as a navigable 3D volume (z = time), which is where the kPad Meta Quest 3 thread connects. The diagram doubles as a living architecture document: the shape of the body is the module map, and a limb with no cells is a module with no tests — visible by construction.

What the data already supports

No new instrumentation is needed for stages 1–2. Every scheduled harness reports test:verdict events into the target environment's kflow log, and results.php already serves them per environment with commit stamps and timestamps. A health map is a pure projection of (test instance × time) → verdict — the same feed the retest grid and kwallet.html read today. The one genuinely new piece of data is the module mapping: a small modules.json assigning every test id to a body region (and every region to a place on the figure). Tests not yet mapped land in an explicit unassigned region — nothing is allowed to hide.

SILENT stays a first-class verdict, exactly as on kwallet.html: each test declares its cadence, and a test that stops reporting renders as decayed/faded tissue, ranked with FAIL. On a body metaphor this is natural — numbness is a symptom, not an absence of news.

Encoding rules (from the dataviz pass)

  • Status is never color alone. The house QA palette's warn/bad pair (#8a5a00/#a12a2a) measures ΔE 4.1 under deuteranopia — effectively identical to red-green colorblind readers. Every cell therefore carries a glyph (✓ ✗ ◌) and SILENT additionally gets the hatch texture + fade. This is a hard rule for every stage, including WebGL.
  • Cell order is stable. Cells sit at fixed positions per module (declared in modules.json), so the eye learns where each test lives — same reason the grid pins its first column.
  • Module health = worst-of its cells, with SILENT ranked as bad as FAIL (kwallet.html's rule, promoted to the whole body). No averaging — an organ with one failing test is not "80% healthy".
  • Empty modules render as dashed outlines. The body doubles as the coverage map: a limb with no cells is the to-do list.
  • Environments are parallel bodies, not merged: lab1 / kswap / PAT / production side by side, each fed by its own results.php. Same organism, different beds — kswap pale next to a green lab1 says "promotion base isn't being exercised" in one glance (exactly today's finding).

Stages

⏳ done / existing Stage 0 — the grid (now). results.html (history × commit, now auto-scrolled to newest) and kwallet.html (current wallet status). These stay; the health map is a lens over the same feed, not a replacement.
⛏ rock Stage 1 — the 2D body. healthmap-live.html: inline-SVG figure, regions + cells from a new modules.json, verdicts from results.php?days=14 per environment, four bodies side by side. Tap a cell → the same run-detail modal the grid uses. No build step, no dependencies — house style.
🪨 stone, after stage 1 Stage 2 — time as a filmstrip. A scrubber (day or commit granularity) replays the body's state from kflow history; a strip of small-multiple bodies for the last N days gives the "health going back in time" read without any 3D. This is where most of the diagnostic value of the z-axis lands, cheaply.
🧗 boulder — needs a conversation Stage 3 — the volume. WebGL (three.js): extrude each cell along z = time into a column of verdicts; the body becomes a tunnel you fly through, scars visible as red/hatched strata. WebXR variant is the Meta Quest 3 connection (kPad thread). Open questions below must be settled first; the 2D stages generate the data shapes and the module taxonomy this consumes.

Open questions (for the stage-3 conversation)

  • Granularity of z. Commit, day, or run? Commits are uneven in time; days are even but blur multi-commit days. The grid already fights this ("pseudo timeline"); the volume makes it structural.
  • One body or per-environment volumes? Four tunnels side by side, or one body with environment as a 4th encoding (the user's "fourth dimension" thought cuts either way — time is the natural z; environment may be the walls).
  • Assertion-level cells? A5 suites carry 8 assertions per instance — do cells subdivide on zoom (body → organ → tissue), or stay instance-level? Zoom-subdivision is the natural VR interaction but multiplies the mapping work.
  • Does the body become the design document of record? If yes, modules.json wants to live next to the architecture docs and be reviewed like one — the diagram is then load-bearing, not decorative.
