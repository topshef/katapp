Katomia QA

This is the testing home for Katomia. New here? The strip below is the live pulse — one chip per test, green/red, greyed if it only runs on demand. Below it, four sections in the order you'll actually ask the questions: is it working, what do we test, when did it break, and how testing works here. What we don't test is stated plainly at the bottom — this page should never look like more coverage than it is.

🩺 Is it working right now?

Current health, one screen per area. Testnet runs constantly (free — "does the logic work"); mainnet runs daily at real cost ("is it true with real money") — a testnet-green/mainnet-red split is information, not a duplicate.

  • Signing health — the wallet/signing tests on one screen; a silent test is ranked as badly as a failing one
  • State sync — the incremental-update layer (STATSYNC1) is guarded daily by T:STATSYNC-01…04; its verdicts appear in the strip above and the grid
  • Transaction log — every mainnet/testnet tx attempted, start→lock→consensus→end

🔬 What do we test — and what does each test actually do?

Every test id resolves here: what it asserts, step by step, how to run it, what a failure means. If an id isn't in the index, it doesn't exist.

  • Test index — every suite and assertion, with runners and repro steps
  • WalletConnect scenario grid — WC path definitions (to be absorbed into the test index)

📉 When did it start failing?

History: verdicts against commits, so a regression points at the change that caused it.

  • Retest grid — commits across, tests down
  • Backend kflow-admin — full event stream (access-controlled)

📚 How do we test, and why?

The process and its reasoning. The first two are current practice; the rest is planning material — it describes ambition, not coverage.

  • Plain-language guide — how testing works here, no jargon
  • Decisions & configuration — why things are the way they are
  • Testing strategy — the aspiration (planning doc)
  • Test dimensions — the axes a full suite would cover (planning doc)
  • katrun index — scripted runs / demo loops (closer to demo tooling than QA — status to be decided)
⚠️ Known gaps — what is NOT tested. Read this before trusting a green strip:
  • Board interaction — no automated test drives offers/withdraw/lock through the real UI (the statsync suites verify board state & rendering equivalence, added 2026-08-14, but not gestures).
  • Order-book mode — no test at all.
  • Auth / commitment flows — no test.
  • Mobile layout — no automated eyes; manual passes are not being recorded.
  • The planning docs above describe more instances/dimensions than have ever reported a verdict — taxonomy is not coverage.
