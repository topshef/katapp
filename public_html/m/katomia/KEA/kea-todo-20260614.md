# KEA Validation Refactor

## Goal

Move all authoritative transaction validation from `kpoolKea.js` (backend) into the KEA client app.

The KEA app is the user's signer and therefore the trust boundary. The backend must not be relied upon for security decisions.

## Current Problem

We currently perform transfer validation and fill validation on the backend and return:

```js
execution.transferCheck
```

The KEA app largely displays this result rather than independently recalculating it.

This is backwards.

A malicious or buggy backend must not be able to influence whether a transaction is considered safe.

## Target Architecture

### Backend responsibilities

Backend should:

- Build the KEA payload

- Package:
  
  - transaction
  
  - mandate
  
  - fill
  
  - pchBasis
  
  - order context

- Return raw data

- Optionally include diagnostic information

Backend should NOT be authoritative.

Example:

```js
transferCheck: {
  status: "diagnostic",
  comment: "backend pre-check only; KEA app performs authoritative validation"
}
```

or remove transferCheck entirely.

### KEA responsibilities

KEA must independently validate everything before signing.

KEA should not trust:

- transferCheck

- status fields

- pass/fail indicators

- backend conclusions

KEA should only trust:

- signed intent

- transaction bytes

- data it can verify itself

## Checks To Move Into KEA

### 1. Intent signature validation

Verify:

```text
intentPayload
+
intentSignature
+
intentPubkey
```

### 2. Bundle hash validation

Verify:

```text
hash(bundle)
==
intentPayload.bundleHash
```

### 3. Network validation

Verify:

```text
intentPayload.network
==
transaction network
==
KEA selected network
```

### 4. Game validation

Verify:

```text
intentPayload.gameId
==
expected gameId
```

(or at minimum verify consistency throughout payload)

### 5. Fill validation

Verify:

```text
fill numerator
fill denominator
```

against the signed order bundle.

### 6. Transfer validation

Recompute expected transfers from:

```text
bundle
×
fill ratio
```

Compare against:

```text
pchBasis.transfers
```

All transfers must be fully explained.

No unexplained residuals.

### 7. Transaction hash validation

Verify:

```text
sha256(txBytesHex)
==
txHash
```

### 8. PCH validation

Verify:

```text
PCH
==
hash(pchBasis)
```

if not already covered elsewhere.

## Development Simplification

During development:

- Keep backend transfer checker if useful for debugging.

- Label it clearly as diagnostic only.

- KEA ignores backend pass/fail results.

- KEA recomputes everything itself.

## Design Principle

The rule should be:

"The backend may help detect problems, but the backend is never trusted."

The only authority is the KEA signer app.
